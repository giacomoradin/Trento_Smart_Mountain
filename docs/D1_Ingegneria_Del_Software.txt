\begin{abstractbox}
\Large
Il presente documento illustra le specifiche dei requisiti e l'analisi preliminare di \textit{Trento Smart Mountain \faMountain\ }, un ecosistema digitale innovativo per l'ambiente montano. L'obiettivo è superare i tradizionali applicativi di navigazione passiva, proponendo una piattaforma attiva che integra due pilastri fondamentali: la gestione della sicurezza dei gruppi attraverso comunicazione offline in mesh, e un framework di economia circolare basato su crediti sociali per incentivare la raccolta e lo smaltimento dei rifiuti in quota. L'architettura, che fonde componenti software e hardware, garantisce affidabilità anche in ambienti critici, offrendo una Unique Selling Proposition orientata alla sostenibilità e alla sicurezza.
\end{abstractbox}

\normalsize
\subsection*{Trasversali}
\textit{Questo requisito si applica a tutti gli attori del sistema.}
\begin{itemize}[itemsep=2pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{RF0}: L'utente deve autenticarsi nel sistema per accedere al servizio.
\end{itemize}
\subsection*{Utente Dinamico}
\textit{I seguenti requisiti si applicano a Partecipante e Capogruppo.}
\begin{itemize}[itemsep=2pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{RF1}: Il sistema deve permettere all'utente di selezionare un itinerario utilizzando gli Open Data.
    \item \textbf{RF2}: Il sistema deve mostrare la difficoltà tecnica e il dislivello dei percorsi.
    \item \textbf{RF3}: Il sistema deve fornire consigli sull'equipaggiamento necessario in base all'itinerario e al meteo.
    \item \textbf{RF4}: Il sistema deve reindirizzare l'utente agli store partner per l'acquisto di attrezzatura mancante.
    \item \textbf{RF5}: Il sistema deve permettere l'invio e la ricezione di messaggi di testo locali (BitChat) tramite protocolli hardware BLE.
    \item \textbf{RF6}: Il sistema deve ottimizzare l'uso del GPS interfacciandosi con l'accelerometro per disattivare il tracciamento da fermo (Auto-Pause).
\end{itemize}

\subsection*{Partecipante (Escursionista)}
\begin{itemize}[itemsep=2pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{RF7}: Il sistema deve permettere al Partecipante di unirsi a un'escursione di gruppo tramite codice invito.
    \item \textbf{RF8}: Il sistema deve tracciare la posizione GPS del Partecipante in background.
    \item \textbf{RF9}: Il sistema deve permettere l'invio di un segnale SOS contenente coordinate GPS precise.
    \item \textbf{RF10}: Il sistema deve mostrare al Partecipante una mappa offline, una bussola e la sua posizione relativa rispetto al gruppo.
\end{itemize}

\subsection*{Capogruppo (Guida Alpina/CAI)}
\begin{itemize}[itemsep=2pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{RF11}: Il sistema deve permettere al Capogruppo di creare una nuova escursione generando un codice invito univoco.
    \item \textbf{RF12}: Il sistema deve mostrare al Capogruppo una dashboard con il tracking GPS in tempo reale di tutti i partecipanti.
    \item \textbf{RF13}: Il sistema deve permettere al Capogruppo di gestire le emergenze e inviare allarmi in broadcast a tutto il gruppo.
\end{itemize}

\subsection*{Gestore Rifugio}
\begin{itemize}[itemsep=2pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{RF14}: Il sistema deve permettere l'inserimento e l'invio di allerte push relative a pericoli immediati.
    \item \textbf{RF15}: Il sistema deve permettere di registrare a sistema un carico di rifiuti, inserendone i dati logistici.
    \item \textbf{RF16}: Il sistema deve associare univocamente un sacchetto di rifiuti (tramite QR code) al profilo dell'utente trasportatore.

\subsection*{Operatore Ecologico (Ecocentro)}
\begin{itemize}[itemsep=2pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{RF17}: Il sistema deve fornire una web-app per scansionare il codice dei rifiuti consegnati a valle.
    \item \textbf{RF18}: Il sistema deve permettere la conferma dello smaltimento assegnando in modo definitivo i Crediti Sociali calcolati all'utente.

\subsection*{Amministratore}

\section{Requisiti Non Funzionali (RNF)}
\small{\textit{Definizione dei vincoli di qualità, performance, hardware e architettura, formulati in ottica testabile.}}
\normalsize
\begin{itemize}[itemsep=2pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{RNF1 (Prestazioni API):} Il tempo di risposta del backend per query geospaziali deve essere $< 500$ ms al 95° percentile in condizioni di copertura 4G.
    \item \textbf{RNF2 (Architettura):} Il sistema deve implementare un pattern \textit{Store-and-Forward} (Offline-first) per garantire la resilienza in assenza di rete.
    \item \textbf{RNF3 (Usabilità):} L'interfaccia "During-Hike" deve essere operabile con una sola mano (pulsanti minimi di $48\times48$ dp) e supportare il Dark Mode ad alto contrasto.
    \item \textbf{RNF4 (Compatibilità):} L'app nativa Kotlin deve supportare Android 9.0 (API Level 28) o superiori.
    \item \textbf{RNF5 (Manutenibilità e Backend):} L'architettura server seguirà il paradigma di \textit{Monolite Modulare} basato su Node.js, utilizzando un database NoSQL (MongoDB).
    \item \textbf{RNF6 (Integrazione):} Il polling verso le API di MeteoTrentino in fase di Pre-Hike deve avere un timeout massimo di 3 secondi prima di mostrare dati in cache.
    \item \textbf{RNF7 (Affidabilità Rete Ibrida):} In assenza di rete internet, il protocollo di chat deve effettuare uno switch automatico da WebSocket a trasmissione BLE Mesh locale entro 5 secondi.
    \item \textbf{RNF8 (Sicurezza):} I payload della chat e le coordinate SOS devono essere crittografati simmetricamente (AES-256) prima del broadcast BLE.
    \item \textbf{RNF9 (Efficienza Energetica):} La logica a stati decrescenti di campionamento GPS e BLE deve garantire un battery drain in background inferiore all'$8\%$ orario (su batteria da 4000 mAh).
    \item \textbf{RNF10 (Storage Ottimizzato):} Il database locale SQLite del dispositivo non deve allocare più di 50 MB per log offline, applicando una policy di cancellazione FIFO a saturazione.
\end{itemize}

\section{Architettura di Sistema e Modelli Dati}
\small{\textit{La presente sezione definisce l'architettura logica e fisica dell'ecosistema Trento Smart Mountain. Vengono dettagliati i design pattern che verranno adottati per il frontend mobile, l'infrastruttura di elaborazione backend, il paradigma di persistenza NoSQL e la topologia di deployment, garantendo la tracciabilità con i Requisiti Non Funzionali (RNF) definiti in precedenza.}}

\subsection{Architettura Software Mobile (Client-Side)}
Per soddisfare i rigorosi vincoli di interazione hardware (RNF9) e operatività in assenza di copertura di rete (RNF2), l'applicativo client è sviluppato nativamente in ambiente \textbf{Android (Kotlin)}. Il design pattern architetturale prescelto è l'\textbf{MVVM (Model-View-ViewModel)}, strutturato per disaccoppiare la logica di presentazione dalla logica di business e di accesso ai dati.

\begin{itemize}[itemsep=4pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{Data/Repository Layer (SSOT):} Il \textit{Repository} agisce da "Single Source of Truth". Intercetta le richieste del \textit{ViewModel} e agisce come un router dati: in presenza di rete, comunica con il backend tramite API REST o WebSockets; in assenza di rete, dirotta le operazioni di lettura/scrittura su un database relazionale locale. Al ripristino della connettività, un \textit{Sync Manager} basato su \textit{Android WorkManager} applica il principio della \textit{Eventual Consistency}, svuotando la coda locale verso il server.
    \item \textbf{Hardware \& OS Abstraction Layer:} Per impedire che l'OS termini i processi di localizzazione e ascolto BLE in background (\textit{Doze Mode}), i moduli critici sono isolati all'interno di un \textbf{Foreground Service} accoppiato a una notifica persistente. 
    \item \textbf{Gestione Energetica (Auto-Pause):} Il campionamento GPS è governato da una Macchina a Stati Finiti (FSM). Un \textbf{BroadcastReceiver} ascolta gli eventi del \textit{SensorManager} (accelerometro). Rilevata un'immobilità superiore a una soglia $T$, il ricevitore GPS viene spento tramite \textit{teardown} logico e il sistema mantiene un \textit{WakeLock} hardware minimo, riattivando il polling spaziale esclusivamente alla rilevazione di un nuovo step cinematico.
\end{itemize}

\subsection{Architettura Backend e Modelli di Calcolo (Server-Side)}
Il backend funge da strato di validazione, sincronizzazione e aggregazione dati. Progettato secondo il paradigma di \textbf{Monolite Modulare}, il server verrá implementato in ambiente \textbf{Node.js}. L'architettura espone due interfacce di comunicazione distinte:
\begin{enumerate}[itemsep=2pt, label=\arabic*.]
    \item \textbf{Livello Stateless (API RESTful):} Gestisce le operazioni Create, Read, Update, Delete transazionali, come l'autenticazione, la creazione delle sessioni di escursione, e l'algoritmo di validazione \textit{Double ACK} dei rifiuti per l'erogazione dei Crediti Sociali ($Sc$).
    \item \textbf{Livello Stateful (WebSockets):} Mantiene i canali persistenti in TCP (full-duplex) per la trasmissione in tempo reale della telemetria, il tracciamento del gruppo e il routing della messaggistica interna (Chat).
\end{enumerate}
\newpage
\subsection{Paradigma di Persistenza e Data Model (NoSQL)}
Considerata l'elevata frequenza di inserimento (scrittura massiva di coordinate) e la natura intrinsecamente non relazionale e destrutturata dei dati di tracciamento, si è optato per \textbf{MongoDB}, un DBMS NoSQL orientato ai documenti (JSON). Questa scelta permette di sfruttare nativamente lo standard \textbf{GeoJSON} e gli indici geospaziali (\texttt{2dsphere}), ottimizzando i tempi di risposta (RNF1) per le query topografiche.

Il dominio informativo è normalizzato in quattro collezioni principali:
\begin{itemize}[itemsep=4pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{Users:} Documento anagrafico che definisce la \textit{Role-Based Access Control} (Utente Base, Capogruppo CAI, Gestore Rifugio, Ecocentro), conservando l'hash crittografico delle credenziali e il saldo aggiornato dei Crediti Sociali.
    \item \textbf{HikeSessions:} Aggregato logico che definisce l'escursione. Contiene un ID univoco, il riferimento (\textit{ObjectID}) del \textit{leader}, le coordinate del percorso pre-hike e un array di riferimenti (embedding) ai partecipanti.
    \item \textbf{TelemetryLogs:} Per mitigare l'overhead di memorizzazione, i dati GPS non generano un singolo documento ciascuno. Si applica il pattern a \textit{Bucket}: un documento copre una finestra temporale (es. 1 ora) per un dato utente, e le singole coordinate/timestamp vengono appese (\texttt{\$push}) in un array interno, riducendo drasticamente le dimensioni degli indici e migliorando l'efficienza in lettura.
    \item \textbf{WasteTransactions:} Documento preposto al tracciamento della logistica inversa dei rifiuti. Registra l'identificativo fisico (QR Code), i fattori architetturali di gamification ($W$ = peso, $D$ = difficoltà, $E$ = emergenza) e modella una macchina a stati (Pending $\rightarrow$ In Transit $\rightarrow$ Validated / Abandoned).
\end{itemize}

\subsection{Infrastruttura di Deployment e CI/CD}
L'infrastruttura verrá progettata per disaccoppiare gli strati applicativi, garantendo scalabilità e resilienza. L'intero ciclo di vita del software è tracciato su repository \textbf{GitHub}, che funge non solo da \textit{Version Control System (VCS)}, ma pilota l'intera pipeline di \textit{Continuous Integration e Continuous Deployment (CI/CD)} attraverso le \textbf{GitHub Actions}.

Dal punto di vista del deployment fisico:
\begin{itemize}[itemsep=2pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{Frontend Ecocentro (Web-App):} Poiché sará un'applicazione statica, verrá pacchettizzata e servita attraverso la \textit{CDN Edge} di \textbf{Netlify}, abbattendo i tempi di caricamento a valle e azzerando i costi di compute.
    \item \textbf{Backend Logico (Node.js):} È containerizzato tramite immagine \textbf{Docker} per assicurare l'immutabilità dell'ambiente di esecuzione.
    \item \textbf{Database:} La persistenza è delegata all'infrastruttura cloud \textbf{MongoDB} in configurazione \textit{Database-as-a-Service}.
\end{itemize}

\subsection{Routing Ibrido Opportunistico (Chat \& SOS)}
Il requisito di continuità operativa in montagna impone un disaccoppiamento logico dal solo strato IP. L'architettura client implementa un \textbf{Connection Manager} in grado di eseguire lo switch trasparente del protocollo di rete:
\begin{enumerate}
    \item \textbf{Modalità IP (Primary):} Sotto copertura 4G/5G, il payload (crittografato AES-256) viene instradato verso il server Node.js via \textbf{WebSocket}. Il server fa da \textit{broker} ed emette il segnale verso i dispositivi in ascolto, garantendo delivery immediata.
    \item \textbf{Modalità Mesh/Decentralizzata (Fallback):} Alla caduta del socket TCP/IP, il sistema attiva un meccanismo di \textit{Graceful Degradation}. Il modulo hardware \textbf{BLE} passa in modalità attiva. Il payload viene iniettato in \textit{broadcast} locale, sfruttando i dispositivi vicini come nodi relè. Questo flooding genera un "cordone ombelicale" digitale che fa rimbalzare il pacchetto da un partecipante all'altro, fino a raggiungere il Capogruppo (o le utenze vicine in caso di SOS), bypassando totalmente la rete cellulare.
\end{enumerate}

\section{Analisi di Mercato}
\small{\textit{Analisi del posizionamento del prodotto, del target di riferimento e del panorama competitivo.}}
\normalsize
\vspace{0.5cm}\\
Per validare la realizzabilità dell'ecosistema \textit{Trento Smart Mountain}, è stata condotta un'analisi quantitativa del mercato di riferimento e della sostenibilità finanziaria. L'obiettivo è dimostrare che l'architettura software proposta risponda a un'esigenza reale, economicamente sostenibile e scalabile, generando valore per tutti gli stakeholder coinvolti.

\subsection{Dimensionamento del Mercato (TAM, SAM, SOM)}
L'ecosistema si posiziona strategicamente all'intersezione tra il mercato del \textit{Digital Health \& Fitness}, quello del turismo esperienziale e quello delle tecnologie per la sostenibilità ambientale. Questa convergenza consente di attingere a flussi di domanda multipli e complementari.

\begin{itemize}[itemsep=4pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{TAM (Total Addressable Market):} Il mercato globale delle applicazioni di navigazione outdoor, tracciamento GPS e fitness attivo. Secondo i report di settore, questo mercato è stato valutato circa 1,5 miliardi di dollari nel 2023, con un tasso di crescita annuo composto (CAGR\footnote{Il CAGR (\textit{Compound Annual Growth Rate}) si calcola come $\left(\frac{V_f}{V_i}\right)^{\frac{1}{n}} - 1$, dove $V_f$ è il valore finale, $V_i$ il valore iniziale e $n$ il numero di anni.}) previsto intorno al 15\% fino al 2030. Piattaforme affermate come Komoot, Strava e AllTrails dimostrano la sostenibilità dei modelli freemium in questo dominio.
    
    \item \textbf{SAM (Serviceable Available Market):} Il bacino del turismo escursionistico sull'intero arco alpino italiano. Le Alpi italiane attirano annualmente oltre 25 milioni di presenze turistiche, di cui una percentuale significativa (stimata tra il 30\% e il 40\%) è motivata da attività outdoor quali trekking, alpinismo e mountain bike. Questo segmento rappresenta un mercato potenziale di circa 8-10 milioni di utenti all'anno.
    
    \item \textbf{SOM (Serviceable Obtainable Market):} Il bacino turistico della Provincia Autonoma di Trento, scelta come mercato di lancio per l'MVP. Con oltre 10 milioni di presenze turistiche annue e una vocazione storicamente radicata nel turismo montano di qualità, il target iniziale è misurabile in circa 1-2 milioni di utenti (considerando il 15-20\% di presenze con profilo escursionistico). Questo volume garantisce la massa critica necessaria per validare gli algoritmi di gamification e testare l'infrastruttura backend in condizioni operative reali.
\end{itemize}

\newpage
\subsection{Sostenibilità Finanziaria: Il Framework a Credito Sociale}
Il modello di economia circolare si fonda su un solido business model B2B2C (\textit{Business-to-Business-to-Consumer}) ancorato al principio del \textbf{risparmio logistico condiviso}. A differenza di modelli basati puramente su pubblicità o abbonamento, questa architettura genera valore reale dalla riduzione dei costi operativi della filiera montana.

\begin{itemize}[itemsep=4pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{Il problema logistico dei rifugi alpini:} I rifugi d'alta quota dipendono quasi esclusivamente dall'elicottero per l'approvvigionamento materiale e lo smaltimento dei rifiuti. Il costo operativo dell'elisoccorso si attesta sui 80-100 euro al minuto di volo. Una singola missione di smaltimento può quindi costare tra i 1.600 e i 4.000 euro. Attualmente, molti rifugi scaricano questo costo sugli escursionisti attraverso una maggiorazione sul coperto (il cosiddetto "contributo elicottero", pari a 1-3 euro a persona).
    
    \item \textbf{Il flusso finanziario del Credito Sociale ($Sc$):} Quando un escursionista trasporta a valle un carico di rifiuti tracciato tramite QR code, abbatte direttamente il costo di volo che il rifugio avrebbe sostenuto. Il "Credito Sociale" emesso dall'app non è una metrica virtuale, ma rappresenta una quota del risparmio netto conseguito dal Gestore. La piattaforma trattiene una percentuale minoritaria (es. 10-15\%) come commissione di sistema, mentre il resto viene convertito in potere d'acquisto per l'utente.
    
    \item \textbf{Impatto e struttura Win-Win-Win:}
    \begin{itemize}[itemsep=2pt, label=\textcolor{primary}{$\circ$}]
        \item \textbf{Gestore del Rifugio (Win):} Riduzione drastica dei costi logistici (fino al 40-60\% annuo) e minore dipendenza dalle condizioni meteorologiche per lo smaltimento.
        \item \textbf{Utente Escursionista (Win):} Conversione della fatica fisica in valore economico (sconti presso i partner). La gamification trasforma il trasporto rifiuti in un'esperienza gratificante e socialmente riconosciuta.
        \item \textbf{Amministrazione Pubblica ed Ecocentro (Win):} Ricezione di rifiuti già tracciati e differenziati, con riduzione dei costi di smistamento territoriale.
    \end{itemize}
    
    \item \textbf{Proiezioni di sostenibilità:} In uno scenario di adozione moderata (5.000 utenti attivi mensili in Trentino), il volume di rifiuti movimentato via app ridurrebbe le missioni in elicottero di 5-15 voli l'anno, generando un risparmio di sistema stimabile in decine di migliaia di euro.
\end{itemize}

\subsection{Vantaggio Competitivo (Unique Selling Proposition)}
La USP di \textit{Trento Smart Mountain} risiede nella creazione di un \textbf{lock-in tecnologico} basato su metriche ESG (Environmental, Social, Governance) misurabili. L'ecosistema non si limita a offrire uno strumento all'utente finale, ma integra verticalmente la filiera del turismo montano.

\begin{itemize}[itemsep=4pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{Differenziazione architetturale:}
    \begin{itemize}[itemsep=2pt, label=\textcolor{primary}{$\circ$}]
        \item \textbf{Sicurezza attiva:} L'uso di protocolli hardware (BLE) per la rete mesh trasforma lo smartphone in un dispositivo di sicurezza preventiva indipendente dalla rete cellulare.
        \item \textbf{Sostenibilità incentivata:} L'algoritmo di validazione Double ACK monetizza il recupero dei rifiuti, creando un circolo virtuoso.
    \end{itemize}
    
    \item \textbf{Strategia di adozione virale (CAC agevolato):} Fornendo a Guide Alpine e Gestori strumenti B2B indispensabili, si innesca un'adozione virale B2C. I professionisti fungono da \textit{ambassador}, richiedendo ai clienti di scaricare l'app (tramite \textit{Codice Invito}) per partecipare alle escursioni in sicurezza.
    
    \item \textbf{Barriere all'ingresso:} L'integrazione profonda con l'ecosistema fisico (rifugi, Ecocentri) e la complessità di gestione dei sensori hardware creano barriere all'ingresso formidabili. Il valore della piattaforma cresce per "effetto rete", rendendo estremamente complessa la replicabilità da parte di competitor puramente software.

    \item \textbf{Go-To-Market (GTM) e Fase Pilota:} L'introduzione sul mercato non avverrà su scala globale, ma tramite un roll-out controllato. L'MVP verrà validato attraverso un progetto pilota in collaborazione con un ente locale (es. una specifica sezione CAI trentina) e un cluster di 3-5 rifugi partner. Questo approccio consentirà di testare il protocollo \textit{Double ACK} sul campo e calibrare la formula del Credito Sociale prima dello \textit{scale-up} su scala provinciale.
\end{itemize}

\section{Analisi di Fattibilità, Vincoli Tecnici e Gestione del Rischio}
Per garantire il successo del progetto in un ambiente di esecuzione critico come quello montano, l'analisi di fattibilità è stata condotta superando le pure ipotesi teoriche a favore di un approccio pragmatico. La strategia si fonda su una rigorosa valutazione dei vincoli hardware, delle policy del Sistema Operativo (OS) e delle capacità operative del team, al fine di allineare gli obiettivi di innovazione con le reali tempistiche di sviluppo.

\subsection{Vincoli Hardware e di Sistema Operativo (OS)}
L'architettura di \textit{Trento Smart Mountain} deve confrontarsi con le limitazioni intrinseche dei dispositivi consumer e degli ecosistemi software in cui opera.
\begin{itemize}[itemsep=2pt, label=\textcolor{primary}{$\circ$}]
    \item \textbf{Limiti del Background Tracking (Doze Mode):} I moderni sistemi Android applicano rigide policy di risparmio energetico (\textit{Doze Mode} e \textit{App Standby}) che sospendono i processi silenti dopo pochi minuti di inattività.
        \begin{itemize}[itemsep=4pt, label=\textcolor{primary}{$\bullet$}]
            \item \textbf{Soluzione adottata:} Il tracciamento avverrà esclusivamente tramite un \textit{Foreground Service} associato a una notifica persistente. Questo obbliga l'OS a mantenere il processo in esecuzione. A ciò si aggiunge la richiesta dei permessi critici \texttt{ACCESS\_FINE\_LOCATION} e \texttt{ACCESS\_BACKGROUND\_LOCATION}.
        \end{itemize}
    
    \item \textbf{Limiti Fisici della Rete Mesh (BLE):} In un ambiente naturale denso (boschi, rocce), il Bluetooth Low Energy (BLE) subisce un drastico abbattimento della portata effettiva, spesso ridotta a meno di 20-30 metri. 
        \begin{itemize}[itemsep=4pt, label=\textcolor{primary}{$\bullet$}]
            \item \textbf{Soluzione per l'MVP:} La messaggistica mesh (\textit{BitChat}) verrà inizialmente limitata a un "cordone ombelicale" di prossimità per il Capogruppo. Per trasmissioni a raggio più ampio (fino a 100 metri in spazi aperti), si valuterà l'integrazione delle API \textit{Google Nearby Connections}, che combinano Wi-Fi Direct e BLE.
        \end{itemize}
    
    \item \textbf{Gestione del Battery Drain:} Il consumo energetico rappresenta una criticità primaria in escursioni prolungate. L'obiettivo di contenere il drain al di sotto del 10-12\% orario è stato definito come KPI per l'MVP. 
        \begin{itemize}[itemsep=4pt, label=\textcolor{primary}{$\bullet$}]
            \item \textbf{Soluzione implementativa:} Il polling del GPS sarà dinamico. Sfruttando l'accelerometro hardware, il sistema implementerà un meccanismo di \textit{Auto-Pause} che riduce la frequenza di campionamento da 1 Hz a 0.01 Hz in caso di immobilità. Inoltre, la trasmissione dati avverrà in \textit{burst aggregati} per ridurre il wake time del modem cellulare.
        \end{itemize}
    
    \item \textbf{Vincoli di Persistenza e Sincronizzazione Dati:} Per supportare pienamente l'approccio Offline-First, l'architettura implementerà un rigoroso pattern \textit{Store-and-Forward}. 
        \begin{itemize}[itemsep=4pt, label=\textcolor{primary}{$\bullet$}]
            \item \textbf{Soluzione implementativa:} Tutti i log di posizione e i payload di emergenza verranno immagazzinati temporaneamente in un database locale cifrato (es. SQLite/Room). Un \textit{Sync Manager} in background si occuperà di sincronizzare asincronamente i dati con il server centrale esclusivamente quando l'OS notificherà il ripristino di una connessione di rete stabile.
        \end{itemize}
\end{itemize}

\subsection{Fattibilità del Motore Gamification e Logica di Reward}
Il motore logico alla base della gamification è stato progettato per essere computazionalmente leggero e, soprattutto, economicamente sostenibile nel lungo periodo. Il premio in Crediti Sociali ($Sc$) è determinato dinamicamente in fase di validazione (\textit{Double ACK}) all'Ecocentro tramite la seguente funzione:
\begin{equation}
    Sc = \Delta \cdot K \cdot (W \cdot D \cdot E)
\end{equation}
Dove:
\begin{itemize}[itemsep=2pt, label=\textcolor{primary}{$\circ$}]
    \item $\Delta \in \{1, -1\}$ (\textit{Outcome}): moltiplicatore di esito. Assume valore $1$ in caso di smaltimento corretto a valle, e $-1$ (penale) in caso di abbandono o manomissione del carico accertata;
    \item $K$ (\textit{Constant}): fattore di normalizzazione economica. Ancora l'emissione dei crediti al reale risparmio logistico conseguito dal rifugio (es. riduzione dei costi dell'elitrasporto), prevenendo l'iperinflazione del sistema;
    \item $W$ (\textit{Weight}): rappresenta il peso netto del rifiuto e la tipologia merceologica;
    \item $D$ (\textit{Difficulty}): moltiplicatore dinamico derivato dagli Open Data, basato sulla difficoltà topografica (dislivello e sviluppo chilometrico del percorso di rientro);
    \item $E$ (\textit{Emergency}): fattore di priorità logistica (es. saturazione dei magazzini) dichiarato dal gestore del rifugio al momento della presa in carico.
\end{itemize}
Per garantire la sicurezza transazionale del framework di economia circolare, il protocollo Double ACK agirà come meccanismo di validazione. Al momento della scansione finale all'Ecocentro, il backend invaliderà definitivamente l'identificativo del rifiuto, prevenendo attacchi di tipo \textit{replay} (scansioni multiple) e garantendo l'assegnazione (o la decurtazione) univoca e definitiva dei crediti sociali. Ai fini della PoC, l'interfaccia dell'Ecocentro sarà simulata tramite un'API mockata, eliminando la dipendenza da infrastrutture esterne e accelerando il ciclo di sviluppo del front-end.

\subsection{Limiti del Team e Strategia di Sviluppo (Time-to-Market)}
L'analisi di fattibilità ha tenuto conto dei seguenti vincoli progettuali legati alle risorse umane:

\begin{itemize}[itemsep=4pt, label=\textcolor{primary}{$\bullet$}]
    \item \textbf{Vincolo Temporale e Skillset:} Il team dispone di 10 settimane per la release finale. Data la prevalente estrazione in ingegneria elettronica dei membri, esiste una fisiologica curva di apprendimento per i framework software ad alto livello (Android SDK, pattern MVVM).
    \item \textbf{Scope Reduction:} Lo sviluppo seguirà un approccio incrementale. La priorità assoluta sarà data allo sviluppo \textit{core} delle interazioni hardware/software a basso livello (lettura sensori, permessi in foreground), dominio di competenza affine al team.
    \item \textbf{Mocking Spinto:} Le funzionalità non vitali per dimostrare la USP (es. API MeteoTrentino, database Amministratori) verranno fornite come \textit{Mock Data} statici.
\end{itemize}
